# AccsMarkets — V2.2.0 Upgrade Plan

Planning document only — nothing in this file has been built. `V2.1.0_UPGRADE_PLAN.md` was a
screenshot-driven redesign of specific M1 surfaces (listing flow, escrow, checkout, messages).
**V2.2.0 is a whole-project sweep** across four pillars you named directly: UX/UI polish to an
"agency level" standard, the missing features/functions a full sweep turns up, workflow gaps, and a
proper live chat system — the one substantial feature that's been flagged as a placeholder ("buy vs.
build, decide later") in every prior plan without ever being fully specified.

## Context & Research

Two things were researched before writing this, not just assumed:

**Live chat, 2026 baseline expectations:** branded widgets (not generic default styling) see
meaningfully higher trust and engagement; canned responses and routing rules are considered
table-stakes, not advanced; offline/away handling and proactive triggers on high-value pages
(checkout, product detail) are standard practice, not novelty. This directly informs Pillar D below.

**"Agency level" UX, 2026 baseline:** generic spinners are now considered an anti-pattern — skeleton
screens that mirror the actual layout are the expected replacement, because they reduce *perceived*
wait time and prevent layout shift. Micro-interactions are expected to be restrained and purposeful,
not decorative. Live, field-level form validation (not just submit-time errors) is expected on any
serious form. This directly informs Pillar A below.

**Revisiting an earlier call:** `MILESTONE_3_PLAN.md` Phase 10 and `MILESTONE_4_PLAN.md` Phase 10
both flagged live chat as "buy a widget, building it in-house isn't worth it" — that was the right
read *at the time*, reasoning from a blank slate. It's worth revisiting now: AccsMarkets already runs
its own Socket.IO server with a working room/event pattern (`socket-server.js`, `lib/socket.ts`) and
an already-built chat UI pattern (`EscrowChat`, `MessageThread`) to extend from. Building on top of
existing real-time infrastructure is a meaningfully different cost proposition than building from
zero, which is why Pillar D below specs an in-house build as the lead recommendation while still
naming the buy-a-widget alternative for comparison — this doc supersedes the earlier lean, not
silently, but because the inputs to that decision changed.

## Design System Additions

- **`Skeleton` primitive** — a pulsing gray placeholder block; composed per-surface into real
  skeleton layouts (a listing-grid skeleton, an escrow-detail skeleton, a message-thread skeleton, an
  admin-table skeleton) rather than one generic shape reused everywhere.
- **Custom empty-state illustrations** — replacing the current emoji-based empty states (watchlist,
  messages, notifications, admin queues) with a small consistent illustration set, each paired with a
  clear headline, one-line explanation, and a primary action — never just "nothing here."
- **Rich toast** — icon + title + optional description + optional inline action button, replacing
  today's plain-text `react-hot-toast` defaults.
- **Command palette (⌘K)** — a searchable overlay jumping to listings, orders, settings pages, and
  (for admins) admin actions, without hunting through nav.
- **Chat launcher bubble** — floating, bottom-right, on public pages; subtle pulse on first appearance
  per visit, unread-count badge once a session is active.
- **Chat panel** — pre-chat form → message view, visually consistent with the existing
  `EscrowChat`/`MessageThread` bubble pattern rather than inventing a third chat visual language.
- **Agent presence dot** — small colored indicator (online/away/offline) next to an admin's identity
  in the live-chat context.
- **Negotiation timeline node** — a chat-thread-style visual for offer/counter-offer history, replacing
  the current flat card list.
- **Bulk-select row pattern** — checkbox column + a contextual action bar that appears once ≥1 row is
  selected, for admin tables.
- **Impersonation banner** — a persistent, impossible-to-miss bar ("Viewing as {user} — Exit") shown
  site-wide whenever an admin is impersonating, so it's never ambiguous whose session is active.

## Pillar A — UX/UI Polish (Agency Level)

**A1. Skeleton loading everywhere.** Every surface that currently shows a spinner or a bare "Loading…"
string — the listing grid, listing detail, escrow detail, message threads, admin tables/queues,
dashboard stat cards — gets a matching skeleton composition instead, so the page's structure is
visible before its data is.

**A2. Empty states.** Replace every emoji-based empty state (watchlist, `/dashboard/messages`,
`/dashboard/notifications`, every admin queue) with the new illustration + headline + explanation +
action pattern, consistently applied rather than styled ad hoc per page.

**A3. Live form validation.** Inline, field-level validation as the user types rather than only on
submit — username availability in settings (checked debounced against the existing uniqueness
constraint), password-match confirmation in reset/register flows, price/amount sanity checks in the
listing wizard and offer forms. Errors should clear the instant the input becomes valid, not only on
the next submit attempt.

**A4. Custom error pages.** `/not-found` (404) and a top-level error boundary (500) currently fall
back to Next.js defaults — genuinely missing, not just under-styled. Both need a branded page: what
happened, a search box or link back to `/listings`, and (for 500) a "report this" link that pre-fills
the contact form with the error context.

**A5. Motion pass.** Subtle route-transition fades (Framer Motion is already a dependency from the
landing page — this extends its use into the dashboard/admin shells, restrained per the research
above, not decorative), success micro-animations on key actions (a checkmark morph on completed
escrow release, on offer acceptance), and toast entrance/exit polish matching the new rich-toast
component.

**A6. Command palette.** ⌘K/Ctrl+K opens a searchable jump-list — listings, own orders/escrows,
settings pages for regular users; additionally admin actions and admin pages for admin sessions.

**A7. Recently-viewed tracking.** A lightweight `localStorage`-backed (no login required) list of
recently viewed listings, surfaced as a "Continue browsing" strip on the homepage and browse page for
returning visitors.

**Done when:** no page in the app shows a bare spinner or an un-styled native error page; every empty
state follows the same illustrated pattern; forms validate live instead of only on submit; the command
palette reliably jumps to any listing, order, or settings page by name.

## Pillar B — Missing Features & Functions

**B1. Multi-item / bundle checkout.** Today, one checkout = one listing = one escrow — there's no way
to buy multiple accounts (even from the same seller) in a single flow. Add a lightweight cart: a
"Add to cart" alongside "Buy now" on listing detail, a `/cart` page listing selections, and a checkout
that either (a) creates one escrow per item with a single combined payment step for UX convenience, or
(b) is scoped initially to same-seller bundles only, which is simpler and covers the most common
real-world case (an agency buying several accounts from one seller at once) — recommended starting
scope is (b), expanding to cross-seller bundles later only if demand shows it's needed.

**B2. Saved/favorite sellers.** Distinct from M2's per-listing watchlist — a "Follow this seller"
action (small, separate from M4's social-follow-for-activity-feed concept; this is simpler: just a
saved list) surfaced as a `/dashboard/saved-sellers` page, useful for buyers who repeatedly purchase
from the same trusted agency.

**B3. Listing comparison tool.** Select 2–3 listings (checkbox on `ListingCard`, a floating "Compare
(2)" bar appears once ≥2 selected) → a side-by-side table of every stat (price, followers,
engagement, account age, monetization, the V2.1.0 analytics fields) for quick evaluation.

**B4. Receipts & invoices.** A downloadable PDF receipt generated on escrow completion (transaction
ID, parties, amount, fee, date — the data already exists in `Transaction`/`Escrow`, this is a
rendering/export feature), useful for agency buyers doing their own bookkeeping.

**B5. Digest email option.** Today notifications are real-time-or-nothing. Add an opt-in weekly digest
email (new offers received, escrows awaiting action, saved-search matches once `MILESTONE_3_PLAN.md`
Phase 6 exists) for users who don't want every event as an individual email.

**B6. In-app "What's New."** A changelog feed distinct from M2's site-wide announcement banners (which
are operational/urgent) — an opt-in, dismissible product-updates feed (bell-adjacent icon or a
`/whats-new` page) for shipped features, useful once this platform starts shipping the backlog in
these planning docs.

**B7. Social proof / live activity.** An anonymized "recently sold" ticker on the homepage
("An Instagram account just sold — $450 · 2 min ago," no identifying details), and a "verified sales"
count shown more prominently on seller profiles than the current trust-score card alone — both are
conversion-proven patterns for marketplace trust-building.

**B8. Category landing pages.** Dedicated SEO-targeted pages (e.g. `/youtube-channels-for-sale`)
instead of only `/listings?platform=YOUTUBE` — a real page with unique copy, FAQs specific to that
platform, and the filtered grid, extending `MILESTONE_3_PLAN.md` Phase 8's SEO investment with actual
indexable landing pages rather than only structured data on individual listings.

**B9. Listing draft persistence.** The creation wizard is currently pure client state — closing the
tab mid-wizard loses everything. Persist a real `DRAFT`-status `Listing` row as soon as Step 1
completes (the model already supports `DRAFT` status from M1), so a user can leave and resume instead
of starting over.

**Done when:** each item above ships as a working, reachable feature — not a stub — with B1 in
particular verified against its recommended same-seller-only starting scope so it doesn't quietly
grow into a cross-seller cart redesign mid-build.

## Pillar C — Workflow Improvements

**C1. Negotiation timeline.** Replace `OfferList`'s flat per-round cards with a proper visual timeline
— each offer/counter-offer as a node on a vertical thread (amount, timestamp, who acted), read
top-to-bottom like a conversation rather than as disconnected cards a user has to mentally re-order.

**C2. Admin bulk actions.** Multi-select checkboxes on `/admin/listings` and `/admin/users` (the new
bulk-select row pattern) with a contextual action bar — bulk-approve, bulk-reject with a shared
reason, bulk-ban — since one-at-a-time admin actions don't scale once listing/user volume grows.

**C3. Admin "view as user" impersonation.** Time-limited (e.g. 15-minute session), fully audit-logged
(`AdminAuditLog` already exists and is the right place to record entry/exit), with the new
impersonation banner persistently visible so there's never ambiguity about whose session is active —
essential for diagnosing support tickets ("what does this user actually see") without asking them to
screen-share.

**C4. Escrow deal templates.** For repeat buyers (agencies purchasing the same type of account
repeatedly): a saved checkout preset (preferred network, standard ownership-transfer email) selectable
at checkout instead of re-entering the same details every time.

**Done when:** admins can act on many listings/users at once instead of one row at a time;
impersonation is time-boxed and fully traceable in the audit log; repeat buyers can check out faster
via a saved template.

## Pillar D — Live Chat System

**Decision needed, with a recommendation:** build in-house, reusing the existing Socket.IO
infrastructure and chat UI patterns already proven by `EscrowChat`/`MessageThread` (recommended,
reasoning above), versus a third-party widget (Intercom/Crisp-style — faster to ship, ongoing
per-agent cost, less integration depth with the escrow/order context). The spec below assumes the
in-house build.

**Data model:** `LiveChatSession { id, visitorId, userId?, status (WAITING|ACTIVE|CLOSED),
assignedAgentId?, startedAt, closedAt, source (originating page URL), rating? (1-5), ratingComment?
}`, `LiveChatMessage { id, sessionId, senderType (VISITOR|AGENT|BOT), senderId?, content, createdAt
}`, `CannedResponse { id, shortcut, title, content, category }`, `AgentPresence { adminId, status
(ONLINE|AWAY|OFFLINE), lastActiveAt }`.

**API routes:** visitor-side `POST /api/livechat/start` (issues an anonymous visitor cookie, creates
a `WAITING` session), `GET/POST /api/livechat/[sessionId]/messages`; agent-side `GET
/api/admin/livechat/queue`, `POST /api/admin/livechat/[sessionId]/claim`, `GET/POST
/api/admin/livechat/[sessionId]/messages`, `GET/POST/PUT /api/admin/canned-responses`, `PUT
/api/admin/presence`. Socket events extend the existing `socket-server.js` pattern: a
`livechat:{sessionId}` room per conversation and a `livechat:queue` room every online agent joins, so
new sessions appear for agents in real time exactly the way new DMs already do.

**Visitor-facing UX/UI:**
- The chat launcher bubble on every public page; clicking opens the chat panel.
- Pre-chat form: name + email (skipped if already logged in — pulled from the session), a short
  "what can we help with?" category dropdown that feeds routing.
- Once started, the chat view reuses the established bubble-message visual language, with a visible
  "Agent is typing…" indicator (the typing-indicator pattern already built for DMs, reused here) and
  file attachment support.
- **Proactive trigger:** after a configurable idle period on checkout or a listing-detail page, a
  small non-modal prompt bubble appears ("Need help with this listing?") — dismissible, never a
  blocking popup, consistent with the "restrained, not theatrical" research finding.
- **Offline fallback:** if `AgentPresence` shows no one online, the widget shows "We're offline — leave
  a message" instead of disappearing; the resulting session is still created and simply waits in the
  queue for the next agent to see it, with a transcript emailed once someone replies.
- **Post-chat:** a quick 1–5 star rating + optional comment once a session closes; a transcript emailed
  to the visitor if an email was captured.

**Agent-facing UX/UI:**
- `/admin/livechat` — a queue view (oldest-first, one-click claim) and an active-chats view (the
  claiming agent's own sessions, tabbed like a real inbox rather than one conversation at a time).
- `/admin/livechat/canned-responses` — shortcut/title/content CRUD grouped by category, with a
  type-ahead (`/shortcut`) insert while composing a reply.
- A presence toggle (Online/Away) in the admin header, backed by `AgentPresence`, so agents control
  their own availability rather than always appearing reachable.
- **Handoff:** a claimed session that turns out to be about a specific existing order can be converted
  into that escrow's own chat thread with one click — avoiding a duplicate parallel conversation and
  tying back into V2.1.0 Area 6's decision to treat chat as one contextually-enriched thread per
  relationship rather than several disconnected ones.

**Done when:** a visitor can start a chat from any public page, reach an available agent in real time
or fall back gracefully to an offline message; agents can claim, reply with canned responses, and set
their own availability; a chat about an existing order can be handed off into that order's own thread
without starting over.
