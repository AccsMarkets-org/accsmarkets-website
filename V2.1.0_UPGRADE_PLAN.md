# AccsMarkets — V2.1.0 Upgrade Plan

Planning document only — nothing in this file has been built. Unlike `MILESTONE_2/3/4/5_PLAN.md`
(forward roadmap phases for net-new capability), **V2.1.0 is a redesign and security-hardening pass
over the already-built Milestone 1 system**, driven by a competitive UX teardown of six reference
screenshots you provided from an established account-escrow marketplace, plus targeted research into
whether the patterns in those screenshots reflect real platform policy or just one competitor's
invented rules. The verdict on that research, up front: **the core mechanic — a mandatory multi-day
wait before account ownership fully transfers — is real, not a competitor's arbitrary choice.**

## Research Findings

YouTube channel ownership can only be transferred on a Brand Account, and the process is: add the
buyer as a Manager, wait a mandatory period, then promote them to Primary Owner. That wait is enforced
by YouTube/Google itself as an anti-hijacking security measure — there is no bypass, no trusted-device
exception, and no support escalation that removes it. Separately, at least one existing competitor in
this exact niche (AccsMarket) independently arrived at 7 days as its minimum enforced transfer window,
and others in the space (Social Tradia, TooFame) run comparable multi-day guarantee windows. This means
the reference screenshots' "7-Day Ownership Security Period" isn't house style — it's the platform
constraint AccsMarkets's own escrow already has to work around (`Escrow.transferDeadline` and
`PlatformSettings.escrowTransferDays` exist in the M1 schema for exactly this reason), just not yet
surfaced to users with the clarity or platform-specific accuracy this teardown calls for.

**Design principle for everything below:** adopt the reference's information density, workflow logic,
and interaction patterns — not its blue color scheme. AccsMarkets's orange/light identity
(`MILESTONE_1_PLAN.md`'s Design System section) stays; every redesign here is specified in terms of
layout, component, and behavior, colored with the existing `brand-*` tokens and status maps.

## Design System Additions

- **Country flag inline** — Unicode flag emoji keyed off a 2-letter country code; no image assets
  needed. Used next to any user/seller name across profile cards, admin lists, and listing cards.
- **Masked-username-with-unlock** — partial-mask rendering (`cele******`) + a small lock icon and
  "Unlock with Premium" prompt; see Area 2's decision note on what unlocks it.
- **Feature-pill row** — small colored capsule tags (reuses the `StatusPill` primitive with a new,
  non-status semantic use — one pill per notable attribute rather than one pill per state).
- **Analytics grid card** — a bordered card with a labeled header and a 2-or-3-column stat grid,
  reused for both the listing detail page and (extended) the seller dashboard.
- **Seller trust card** — deals / volume / reviews + star rating + thumbs-up ratio; one component
  reused in three places: listing detail sidebar, message thread sidebar, and (compact variant)
  listing cards.
- **Offers mini-panel** — best-offer highlight + a short offer-history list + Send Offer/Buy Now
  actions, for the listing detail sidebar.
- **Payment-method tile** — a selectable card row (icon, label, description, balance/status),
  designed now as a multi-method pattern even though only Wallet Balance exists today, so `M3`'s
  card payments and `M5`'s bank/virtual-card payouts drop in without a checkout redesign later.
- **Inline warning box** — amber (informational-caution, e.g. insufficient balance) and red
  (compliance-critical, e.g. the transfer-window "don't do this") variants of the same bordered-box
  pattern, distinguished by color and icon, not by two different components.
- **Escrow summary bar** — a compact, embeddable version of the full `EscrowStepper` (transaction ID,
  status pill, mini stepper, live countdown, View link) sized to sit inside a chat thread header.
- **Live countdown** — a client-ticking `Xd Xh Xm Xs remaining` component computed from a server
  timestamp (not a client-only timer, to stay correct across tab refreshes/timezones), reused by the
  escrow transfer window and, cosmetically, the offer-expiry display.
- **Onboarding tile picker** — large single/multi-select tiles (icon + label), reused across the
  onboarding flow's location/intent/platform/reason steps and already visually consistent with the
  listing wizard's existing platform-grid picker.
- **Password strength meter** — a live-updating bar replacing the current static hint text on
  register/reset-password.
- **Settings sub-nav** — a left-nav or tab-strip splitting `/settings` into Profile / Security /
  Sessions / Verification / Notifications / Payment Methods, replacing today's single flat page.

## Area 1 — Listing Security Gate (Verify Before List)

**Current state:** `POST /api/listings` checks `kycLevel !== NONE` at submission time — a user can
fill out the entire 3-step wizard and only discover they're blocked on the final submit.

**Upgrade:** move the check to the front. `/dashboard/listings/new` itself checks verification status
server-side *before* rendering the wizard. Below the required level, the page renders a full "Verification
Required" gate instead: an icon, a headline ("Verify your account to start selling"), a short
explanation of why (fraud prevention, buyer trust — sellers who skip this are the #1 source of scam
reports on comparable platforms), a compact step tracker showing what's done vs. missing (Email ✓ /
Phone ○ / ID ○, tying into `MILESTONE_2_PLAN.md` Phase 6's KYC stepper), and a single primary CTA
into `/settings/verification`. The wizard's own Step 1 keeps a defense-in-depth check too, in case the
gate is ever reached in an inconsistent state.

**Decision embedded here:** this is also the natural moment to decide whether Milestone 1's EMAIL-level
gate should be raised to PHONE now rather than waiting for `MILESTONE_2_PLAN.md` Phase 6's phone
verification to ship — recommended to hold at EMAIL until phone verification actually exists, since
gating on a level nobody can reach yet would just block all selling.

**Done when:** an unverified user visiting the listing-creation route never sees the wizard form at
all, only the verification gate; the gate correctly reflects real-time verification status and routes
straight into the verification flow.

## Area 2 — Listing Details: Extra Fields & Analytics

**Data model additions to `Listing`:** `lifetimeViews (Int?)`, `lifetimeRevenue (Decimal?)`,
`channelRpm (Decimal?)`, `audienceLanguage (String?)`, `strikesWarnings (String?)`, `adsenseStatus`
(enum: `ON | OFF | CHANGEABLE`), `standingStatus` (enum: `GOOD_STANDING | WARNING | STRIKE`).

**Deliberate deviation from the reference:** the reference platform shows an "Escrow Accepted" pill,
implying some listings on *their* platform skip escrow. AccsMarkets's escrow is mandatory for every
sale — so that pill would be redundant noise here and is dropped rather than copied.

**Decision needed:** the masked-username-behind-Premium-unlock pattern is a monetization mechanic, not
a pure UX one — it needs a decision on what unlocks it (a subscription-tier perk on `M2`'s paid plans,
or a standalone pay-per-unlock micro-transaction). Not resolved here; flagged for product/pricing
input before building.

**UX/UI — listing detail page:**
- Masked seller handle + external-link icon + "Ownership Verified" badge in the header.
- The existing 4-stat pill row (subscribers/price/listed-date/category) stays, styling upgraded to
  match the reference's icon-over-value tile treatment.
- New feature-pill row: Monetized, Adsense status, Monthly earnings (Escrow Accepted omitted, as above).
- New Analytics grid card (Design System Additions) showing the new fields, with `standingStatus`
  rendered as a colored badge (green/amber/red) rather than plain text.
- Two new horizontal strips: "Similar accounts for sale" (already planned as ML-quality similarity in
  `MILESTONE_5_PLAN.md` Phase 10; a simpler facet-based version can ship now) and "Seller's other
  accounts for sale" (a straightforward query against the current seller, no new infra needed).
- Sidebar rebuilt around the new Seller trust card + Offers mini-panel + a sponsored-listings slot
  (feeding `MILESTONE_2_PLAN.md`'s promotions feature once built).

**UX/UI — listing wizard step 3:**
- Step labels relabeled "Find / Verify / Submit" (benefit-oriented, matching the reference — a copy
  change over the current generic "1 / 2 / 3").
- Monetized toggle upgraded from a checkbox to a segmented Yes/No control.
- A new "✦ Channel Analytics" bordered sub-section collecting the new fields.
- A "Description Rules" box shown **proactively above the textarea**, not just enforced silently on
  submit — its copy should be generated from the actual categories in `lib/moderation.ts` (scam
  patterns, spam patterns, off-platform contact bait) so the displayed rules and the enforced rules
  can never drift out of sync with each other.
- A live character counter on the description field.
- A "reviewed within 12–48 hours" notice set from `PlatformSettings`, not hardcoded.

**Done when:** the new fields are collected in the wizard and rendered on the detail page; the
Description Rules copy is generated from the real moderation categories; the analytics card and
feature pills render correctly with sensible empty states when optional fields are unset.

## Area 4 — Dashboard & Admin Analytics (Geo + Channel-Analytics Views)

**Data model:** `User.countryCode` (ISO 3166-1 alpha-2). **Decision needed:** source of truth —
self-reported during Area 5's onboarding (recommended primary source, since IP geolocation is
unreliable and trivially defeated by a VPN) versus IP-based geolocation at registration. Recommended
approach: self-reported is the *displayed* value; IP-based geolocation still runs in the background as
a **mismatch signal** feeding `MILESTONE_3_PLAN.md` Phase 4's risk scoring (a large self-reported vs.
IP-detected mismatch is a mild fraud signal, not proof of anything on its own).

For real listing-view analytics (a proper time series rather than the current single cumulative
`Listing.viewCount` integer), add `ListingViewEvent { listingId, viewerHash, createdAt }` — a
lightweight log table, `viewerHash` being a non-reversible hash of session/IP rather than raw PII.

**UX/UI:**
- Country flag (Design System Additions) shown next to any user/seller name: profile cards, admin
  user list rows, listing card seller lines.
- Seller-mode dashboard gains a per-listing mini analytics section (a small sparkline-style chart of
  views over time, sourced from `ListingViewEvent`) — genuinely new capability, not just a restyle,
  since the current schema can't produce a time series.
- Admin dashboard gains a country-breakdown widget (a simple bar list: top countries by user count),
  directly answering "detect with country flags" as a growth/fraud-visibility signal, not just cosmetic.
- Admin user list rows show the country flag inline.

**Done when:** country data is collected and displayed consistently everywhere a user's identity is
shown; sellers can see real per-listing view trends instead of only a lifetime count; admin has a
country-level view of the user base.

## Area 5 — Registration Onboarding Flow

**Data model:** `User.onboardingCompletedAt`, `primaryIntent` (enum: `BUYER | SELLER | BOTH`),
`sellIntentPlatforms (Json)` (which platforms they expect to list, if selling), `sellReason` (enum:
`NO_LONGER_NEEDED | FUNDING_NEW_PROJECT | DIVERSIFYING | OTHER`, `+ freeText` for OTHER),
`countryCode` (the authoritative self-reported value from Area 4).

**UX/UI:** a dedicated `/onboarding` route, redirected into immediately after email verification (or
first Google OAuth login) — **skippable at every step**, never a hard block on dashboard access, since
forcing it would just add friction without the data being any more honest. 3–4 short steps using the
new onboarding tile picker: (1) location — a searchable country select with flags; (2) intent —
Buyer/Seller/Both as three large tiles; (3), shown only if Seller/Both — which platforms they plan to
list, reusing the exact platform-grid pattern already built into the listing wizard's Step 1 for
visual consistency; (4), shown only if Seller/Both — why they're selling, as reason tiles. A visible
"Skip for now" link persists across every step.

**What the data feeds:** Area 4's country/flag features; a personalized dashboard empty-state (a
`primaryIntent = SELLER` user's dashboard leads with "Create your first listing" more prominently than
a buyer's would); a sensible default locale once `MILESTONE_4_PLAN.md` Phase 1's i18n work exists.

**Done when:** the onboarding flow appears once, immediately post-verification, is fully skippable,
and its answers are visible in the collected `User` fields and reflected in at least one personalized
dashboard surface.

## Area 6 — Advanced Messages UX/UI

**Architectural decision — the significant one in this upgrade:** the reference screenshots show
escrow-context (status bar, stepper, countdown) embedded directly inside a normal DM thread, rather
than living only on a separate `/dashboard/escrows/[id]` page as M1 built it. Recommended: **treat
this as one conversation per person, contextually enriched**, not two disconnected chat systems. When
two users share an active or past escrow, their single DM thread (already keyed by sorted user IDs)
also surfaces the escrow's summary bar in the thread header — `Message.escrowId` already exists in
the schema for exactly this kind of correlation, so this is a query/UI change more than a data-model
one. The dedicated escrow detail page (Area 9) still exists for the full picture (deal terms,
participants, actions) — chat becomes the fast/glanceable surface, the detail page stays the complete
one.

**UX/UI:**
- Conversation list: an escrow-status pill on any conversation row tied to an active escrow (e.g.
  "Transferring"), so status is visible without opening the thread.
- Archive tab in the conversation list — the backend (`PUT /api/messages/archive`) already exists
  from M1 and was simply never given a UI tab; this is close to a pure front-end addition.
- Thread header: the new escrow summary bar (Design System Additions) appears whenever the two
  participants have a relevant escrow, collapsible, with a "View full details" link into the escrow
  detail page.
- Thread sidebar: the Seller trust card (Area 2's component, reused) plus a compact "Active listings"
  count for the counterparty.

**Done when:** DM threads correctly surface escrow context when relevant without requiring navigation
away from chat; the archive tab works against the already-built backend; the trust panel renders
correctly for any counterparty, seller or buyer.

## Area 9 — Advanced Escrow Workflow

**Data model:** replace the single global `PlatformSettings.escrowTransferDays` with a
`PlatformTransferPolicy { platform, transferDays, policyNote }` lookup table — YouTube defaults to 7
days with a policy note citing the real Google Brand Account requirement researched above; other
platforms get an admin-configurable default (1–3 days is reasonable pending real data) with their own
note. A single global number was never accurate to begin with, since the underlying constraint is
genuinely platform-specific.

**Explicit non-change:** the countdown becoming more visible and more precisely-timed does **not**
mean completion becomes automatic. Buyer-confirmed completion stays the release trigger — auto-releasing
funds purely because a timer elapsed would be a regression in buyer protection, not an improvement.
What the timer elapsing *does* trigger: a notification to both parties that the window has closed and
the buyer should complete final verification/confirmation.

**UX/UI:**
- The live countdown component (Design System Additions) replaces the current static
  `transferDeadline` date display on the escrow detail page, computed from the server timestamp so it
  stays correct across refreshes.
- A red "Important Notice" box (Design System Additions, compliance variant) appears during the
  transfer stage with platform-specific guidance pulled from `PlatformTransferPolicy.policyNote` —
  for YouTube, concretely: don't manually promote the buyer to Owner, don't modify roles/permissions,
  don't alter access levels during the window, and what happens (full responsibility shifts to the
  seller) if they do it anyway.
- A themed support card with a direct "Chat with Escrow Support" button — this reuses the *existing*
  escrow chat, where admins already have posting rights per M1, rather than standing up a separate
  live-support channel; it's a clearly-labeled entry point, not new backend.
- A proactive "Leave a review" banner appears once the escrow is eligible (post-`COMPLETED`), ahead of
  `MILESTONE_2_PLAN.md`'s review feature actually being live — the banner and mechanism ship together
  when that phase lands.

**Done when:** the transfer window's length is correctly platform-specific rather than one global
number; the countdown is live and server-anchored; the Important Notice content is admin-editable per
platform rather than hardcoded; completion still requires explicit buyer confirmation regardless of
timer state.

## Area 10 — Advanced Checkout

- The order-summary card shows the escrow fee as both a percentage and a dollar amount (e.g. "Escrow

**Done when:** checkout visually matches the reference's density and reassurance signals while every
underlying number (price, fee, total) still comes from the same server-computed `calculateEscrowFee`
call already in place — this is a presentation upgrade over trusted logic, not new fee math.

## Area 11 — Advanced Deposit/Withdrawal UX/UI

No reference image was given for this pair; direction below extrapolates the density/pattern language
established in Areas 1–10.

- **Deposit:** the crypto flow becomes a visible mini-stepper (Select network → Generate address →
  Awaiting payment → Confirmed) instead of a flat form-then-result swap; a real rendered QR code
  (currently the address is shown as text only — genuinely missing today, not just under-styled) makes
  mobile-wallet payment materially easier; the Crypto/Manual toggle becomes the same payment-method
  tile pattern used at checkout for visual consistency across the app; the post-submit state shows a
  live "waiting for confirmation" indicator rather than a static message.
- **Withdrawal:** the network/address form gains the same payment-method-tile framing (ready for
  `MILESTONE_5_PLAN.md` Phase 8's bank/virtual-card options to slot in later); an estimated
  processing-time notice; and — a genuine gap worth closing regardless of the reference — a "Recent
  withdrawal requests" mini-table scoped to this page, since today the only place to see withdrawal
  history is the wallet page's general transaction table mixed in with everything else.
- **Wallet overview:** surface the Available vs. Reserved balance split. The server-side reservation
  logic (pending withdrawals count against available balance) was already built in M1's withdrawal
  route — it's simply never shown to the user today, who sees one balance number with no explanation
  of why a new withdrawal request might be rejected as insufficient.

**Done when:** deposit and withdrawal both read as guided, stateful flows rather than one-shot forms;
the QR code actually renders; withdrawal history has its own visible surface; the available/reserved
balance split — logic that already exists — is finally visible to the user it affects.
